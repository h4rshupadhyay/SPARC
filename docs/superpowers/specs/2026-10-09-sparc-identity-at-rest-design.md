# F1: persistent identity encryption at rest

> **Platform scope update — 2026-10-09:** The user withdrew Windows compatibility and selected a borrowed MacBook for the demo. The demo target is now Linux ↔ macOS. Windows implementation notes below are retained as historical context; real Windows tests and measurements are no longer required gates and have not passed. F1 can close on its recorded Linux verification and independent review. macOS compatibility changes and native Mac demo validation are a separate follow-up before the physical-device demo; neither is inferred from Linux results.

Status: **Proposal awaiting user review.** No product implementation, dependency change, or F1 completion is authorized by this document. Written-spec approval permits preparation of the implementation plan; implementation follows approval of that plan and its execution method.

Date: 2026-10-09. Baseline: A3 verified and committed at `b53453b`.

## Intent and scope

Encrypt the persistent Ed25519 private identity in `identity.json` before T1 begins. Preserve the exact existing private/public key pair, SHA-256 public fingerprint, trusted-peer records, audit signatures and checkpoints when migrating version 1. A failed or canceled operation must never choose a new identity as a recovery action. The execution order remains A3 → F1 → T1 → T2 → T3; existing pending F1 status entries remain unchanged.

The scope is local identity storage, its startup unlock interfaces, diagnostics, and affected callers/tests. It excludes password reset/recovery, passphrase changes, OS credential-vault integration, inactivity locking, trust/audit format changes, network protocol changes, and analysis/traffic changes.

The threat addressed is disclosure or offline copying of a locked identity file, including encrypted temporary files. The public key, salt, KDF parameters and encryption timestamp remain public. Encryption cannot protect a running unlocked Python process from malware, administrators, memory inspection or old plaintext backups. Losing the passphrase means losing the ability to use that identity; SPARC must offer no automatic reset or replacement. Migration cannot securely erase previous filesystem blocks or external backups.

## Recommended approach and alternatives

Use a user-entered passphrase on both Linux and Windows. Derive a 32-byte encryption key with `cryptography` Argon2id, then use its high-level Fernet authenticated-encryption recipe. Serialize the Ed25519 private key with its DER PKCS8 serializer, entirely in memory. Store only the Fernet token and public derivation metadata. This follows the library's documented password-to-Fernet composition and avoids implementing cipher modes, MACs, padding, nonce generation or KDF primitives. The bounded JSON envelope below is application serialization, not a new cryptographic algorithm. [cryptography 50.0.2 Fernet](https://cryptography.io/en/50.0.2/fernet/)

The repository already pins `cryptography==50.0.2`. Adopt one fixed profile: Argon2id, `length=32`, `memory_cost=65536` KiB, `iterations=3`, `lanes=4`, a fresh 16-byte CSPRNG salt, and no extra `secret` or `ad` inputs. The 64 MiB/three-pass selection uses the memory-constrained recommendation referenced by the library; OWASP also recommends Argon2id for resistance to offline password guessing. Applying those password-cost recommendations to identity encryption is this design's inference, not a claim that OWASP specifies this file format. [cryptography Argon2id](https://cryptography.io/en/50.0.2/hazmat/primitives/key-derivation-functions/#argon2id), [OWASP password storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)

Two alternatives were considered:

| Approach | Benefit | Reason not selected for F1 |
| --- | --- | --- |
| Passphrase-encrypted PKCS8 using `BestAvailableEncryption` | Smallest persistence change; standard encrypted-key serialization | The curated encryption choice can vary by library/OpenSSL version. This interface does not expose the explicit memory-hard password profile and authenticated public metadata contract chosen here. This is not a claim that library PKCS8 encryption is broken. [Library serialization](https://cryptography.io/en/50.0.2/hazmat/primitives/asymmetric/serialization/#cryptography.hazmat.primitives.serialization.BestAvailableEncryption) |
| Windows DPAPI plus Linux Secret Service/keyring | Can avoid repeated user prompts; OS manages the unlock secret | Different account/session behavior, headless dependencies and recovery/portability rules expand this milestone. DPAPI normally binds decryption to a user's credentials and computer. [Microsoft DPAPI](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata) |

Argon2id backend absence or insufficient memory is an actionable startup error. Do not silently reduce its cost, fall back to plaintext, select another KDF, or generate another key. Measure startup cost with the prescribed profile on actual Linux and Windows before F1 milestone completion/release approval; compatibility must be demonstrated rather than inferred from Linux platform mocks. Unsupported installations must use a supported `cryptography` build. [Argon2id backend/error contract](https://cryptography.io/en/50.0.2/hazmat/primitives/key-derivation-functions/#argon2id)

## Version-2 storage contract

`identity.json` remains the only identity data file. The exact outer fields are:

| Field | Required value |
| --- | --- |
| `version` | Integer `2`, never Boolean |
| `public_key` | Canonical standard Base64 of the existing 32 raw Ed25519 public bytes |
| `encryption` | String `fernet` |
| `kdf` | Object with exactly `name`, `salt`, `memory_cost`, `iterations`, `lanes`, `length` |
| `encrypted_private_key` | Canonical URL-safe Base64 Fernet token as an ASCII string |

The KDF object's `name` is `argon2id`, `salt` is canonical standard Base64 of exactly 16 bytes, and integer parameters must equal the fixed profile above. Do not pass arbitrary stored cost parameters into a KDF. A changed profile requires a separately reviewed future format/version.

Fernet plaintext is canonical JSON with exactly `domain`, `header`, and `private_key_pkcs8`. `domain` is `SPARC identity at rest v2`; `header` copies the complete outer `version`, `public_key`, `encryption`, and `kdf`; `private_key_pkcs8` is canonical standard Base64 of DER PKCS8 bytes serialized by `cryptography`. `NoEncryption()` applies only to that in-memory serialization before Fernet encryption; no unencrypted serialization is written to disk. Loading authenticates the token first, parses the inner object, requires exact header equality, loads DER with `load_der_private_key(..., password=None)`, requires an `Ed25519PrivateKey`, and verifies its raw public bytes exactly match the header. The returned fingerprint remains `sha256(public_bytes).hexdigest()`. [Library serialization](https://cryptography.io/en/50.0.2/hazmat/primitives/asymmetric/serialization/)

Fernet has no associated-data argument; the encrypted header copy binds public metadata after successful decryption. A tampered salt produces authentication failure; a changed public key is rejected by header/key comparison. Public metadata inspected without unlock remains unauthenticated. Decrypt without a TTL: an identity must not expire because of wall-clock changes. Token timestamps are intentionally public. [Fernet authentication and timestamp behavior](https://cryptography.io/en/50.0.2/fernet/)

Apply bounds before decoding or expensive cryptography: file reads stop at 4097 bytes and reject anything above 4096; token ASCII length is at most 2048; decrypted JSON is at most 1024 bytes; decoded DER is at most 128 bytes. Check schema/types, canonical Base64, exact fields and fixed parameters, including rejection of duplicate JSON keys, unsupported versions and deeply nested invalid documents using the existing strict parser. Restrict identity files to regular files; reject symlinks, dangling links and Windows reparse-point identity files as errors, never as absence. File I/O must not follow an identity-file link during private reads or publication.

No plaintext passphrase, derived key, PHC string containing the derived key, raw private key, or separately persisted decryption secret is stored alongside the ciphertext. Salt and cost metadata are not secrets. OWASP recommends maintained cryptographic libraries, authenticated encryption and protection/separation of encryption secrets; this design supplies the secret through user input. [OWASP cryptographic storage](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html)

## Credentials and application interfaces

Introduce an explicit credential-provider contract owned by the identity module:

- `IdentityUnlockRequest`: public-only immutable request with `purpose` (`create`, `migrate`, `unlock`), `data_dir`, and optional public `fingerprint` labeled unverified. It contains no key material or passphrase.
- `IdentityCredentials`: passphrase bytes plus optional confirmation bytes, with secret fields excluded from representations. Providers return this object or `None` for cancellation. Both values are required and equal for `create`/`migrate`; confirmation must be absent for `unlock`.
- `CredentialProvider = Callable[[IdentityUnlockRequest], IdentityCredentials | None]`.
- `load_identity(data_dir, *, credential_provider=None, cancelled=None) -> Identity` loads, explicitly migrates, or creates as below. Missing provider raises `identity_credentials_required`; it never prompts, supplies a default, or mutates storage. `cancelled` is an optional zero-argument predicate. Existing internal load/create helpers receive explicit credentials instead of discovering them globally.
- `inspect_identity(data_dir) -> IdentityInfo` reads public metadata without mutation, private-key parsing or KDF work. It returns `absent`, `legacy_unencrypted`, or `encrypted_locked`, public bytes/fingerprint when present, and `private_key_verified=False`. Unsupported/corrupt/unreadable files raise an error rather than appearing absent.
- `PeerService(data_dir, limits=Limits(), *, credential_provider=None, cancelled=None)` forwards the explicit provider/predicate and completes identity unlock before constructing `TrustStore`, `AuditLog`, exporting checkpoints, publishing events or creating any workers/listeners. It does not retain provider, credentials or derived encryption key.
- Internally, `_unlock_store` supplies an opaque `_UnlockedStore` containing the unlocked `Identity`, resolved identity path and bounded committed-file snapshot. `load_identity` returns its `Identity`; GUI startup uses `PeerService._from_unlocked_store(handle, limits=Limits(), *, cancelled=None)` instead. This private factory checks cancellation and revalidates that the file matches the handle under the identity lock before constructing service state. A changed target is `identity_changed`. The handle's representation excludes private material; arbitrary `Identity` objects are not accepted by this factory.

Adapters encode user text as strict UTF-8, without normalization, trimming or truncation. Accept all ordinary Unicode and spaces. New/migrated passphrases require at least 15 Unicode characters in text adapters, and library credentials at least 15 bytes; all passphrases are limited to 1024 UTF-8 bytes. The provider API also supports high-entropy byte credentials for automated tests. Unlock accepts any nonempty bounded bytes so future policy changes do not lock out existing users. Explain that a long unique phrase is needed for offline guessing resistance; length validation cannot guarantee entropy. Creation/migration must display and confirm the new phrase before disk mutation. Invalid/mismatched confirmation is `identity_credentials_invalid`, not cancellation or corruption.

Do not add passphrase argv flags, environment variables, credential-file inputs, logs, reports, audit records, event payloads or remembered default secrets. Release references to provider results, text widgets, plaintext DER and derived keys promptly after use; retain only the unlocked signing key for the service lifetime. Python/library allocations cannot guarantee memory zeroization; the design must not promise it. Error messages use fixed safe summaries, not underlying data or credential representations.

The core performs one attempt per call. GUI can offer an explicit Retry after `identity_unlock_failed`; terminal callers return failure and users can rerun. Authentication failure combines incorrect credentials and ciphertext tampering into `identity_unlock_failed`; recognizable schema/key mismatches use `invalid_identity`. Neither path writes anything or generates a new key.

## Migration, publication and failure behavior

Only true absence in a new local state permits creation. If `identity.json` is missing while any trust store, audit log or audit checkpoint exists, raise `identity_missing`; do not silently replace a lost identity. Broken links, access errors and malformed files are never treated as missing.

For version 1, bounded-read and validate its exact existing schema, canonical 32-byte key encodings and private/public match before requesting `migrate` credentials. Keep its bytes and key solely in memory. Obtain and confirm a new passphrase, serialize/encrypt the existing key, decrypt the proposed candidate in memory, then verify the exact private/public pair and fingerprint. Do not generate a key during migration. Check cancellation before and after every expensive library call and before publication. There is no continued legacy plaintext service mode if migration is canceled or fails.

Publication uses a same-directory encrypted-only temporary file with private permissions, flush and file `fsync`, then the final atomic rename/replace. Private identity reads/commits share a short cross-process OS lock associated with a private `.identity.lock`: Linux `fcntl` advisory file locking and Windows `msvcrt` byte-range locking. This lock file contains no secrets. Acquisition polls cancellation at most every 50 ms and fails with `identity_busy` after two seconds; do not wait indefinitely or delete another process's lock. Keep no lock while a user is entering credentials. Read-only public inspection opens one bounded snapshot without creating a lock file. Under the commit lock, reread and compare the target to the original bounded snapshot, and check cancellation again; changed state produces `identity_changed` and no publication. A competing create reports `identity_changed` and requires an explicit retry against the winning identity, never replaces it. The lock serializes cooperating SPARC processes, not a malicious unlocked account. Supported local filesystems must provide atomic same-directory publication; unsupported locking/permissions is an actionable failure.

| Outcome | On-disk identity and startup result |
| --- | --- |
| Wrong credentials, malformed file, provider absent, confirmation mismatch, canceled before publication | Original identity bytes unchanged; no new identity; no service/trust/audit mutation |
| KDF unavailable, permission failure, candidate verification failure, temp write/file flush failure, replacement failure before commit | Original identity bytes unchanged; encrypted temp cleaned up; safe domain error; no service |
| Atomic publication succeeds | Version 2 contains exactly the same identity for migration, or the explicitly created key for a genuinely new store |
| Parent-directory sync/readback fails after publication | Commit outcome/durability uncertain; stop startup with `identity_commit_uncertain`. Never roll back to plaintext, overwrite again, regenerate, or claim original bytes survived. A later explicit unlock reloads the actual file and validates it |
| Cancellation observed after publication | Keep the encrypted same identity; exit canceled before service construction. Do not undo successful encryption |

The irreversible boundary is successful publication, not completion of the encompassing helper. Current `atomic_write` calls `os.replace` before Linux directory synchronization and can therefore raise after replacing the representation. F1 needs an identity-specific publication result that distinguishes these outcomes without changing unrelated writers' error behavior. Atomic replacement alone is not a cross-platform power-loss durability guarantee. [Python replacement semantics](https://docs.python.org/3/library/os.html#os.replace)

No plaintext backup or temporary copy is created. A crash before publication leaves the original v1/v2 or no identity; a crash after it leaves the encrypted same-key representation, subject to filesystem durability. Cleanup must touch only this operation's owned encrypted temporary file. Restart must never auto-select an orphan temp or treat a damaged identity as absent. Repeated reads of valid version 2 do not rewrite it or generate a new salt/token.

Migration writes no trust records, audit records or checkpoints. Subsequent successful service construction retains existing audit recovery/verification behavior; it may perform the same checkpoint export it does today. Migration regression checks compare audit/trust files before that service construction, then prove existing signed history and subsequent records verify with the original public key.

## Linux and Windows behavior

The same encrypted format and passphrase work on both systems; copying an encrypted identity requires that passphrase. Defaults remain `$XDG_CONFIG_HOME/sparc` or `~/.config/sparc` on Linux and `%LOCALAPPDATA%/SPARC` on Windows. No passphrase is obtained from those environment variables.

Linux retains directory mode `0700` and identity/temp/lock mode `0600`. For Windows, enforce a protected DACL allowing the current user's SID and LocalSystem on the SPARC directory and identity/temp/lock files, using Windows security APIs through a narrowly scoped standard-library adapter; no new Python package is needed. Apply file restrictions before publication and check directory ownership before changing it. An explicit data directory must be a dedicated user-owned SPARC directory, not a shared directory. Fail closed on a filesystem that cannot establish the requested ACL or on an unowned/shared directory; do not translate POSIX mode bits into a Windows privacy claim. Do not weaken existing tighter permissions. This permission enforcement is confined to F1 private storage; no unrelated ACL-management feature is introduced. Windows DACLs express user/group access rights and should be manipulated through security APIs. [Microsoft security descriptors](https://learn.microsoft.com/en-us/windows/win32/secauthz/security-descriptors)

Restricting permissions may change permission metadata on an existing identity, including before an operation ultimately fails; the preservation guarantee concerns the identity bytes/key, not retaining insecure permissions. Credential cancellation/absence before private storage preparation makes no permission change. `--check` never changes permissions. Actual Windows NTFS tests must exercise DACLs, file locking, replacement with existing handles, Unicode input, cancellation and backend support; Linux mocks do not establish Windows correctness.

## GUI, CLI diagnostics and simulations

`launch` creates the Tk root and a masked unlock/setup dialog first. `create` and `migrate` show two fields; `unlock` shows one. Migration explains that the existing fingerprint is retained. Cancel, Escape and window close all signal cancellation. No service, tabs, service polling timers, networking or audit persistence exist before identity success. Run KDF/unlock work in one startup worker; keep Tk interactions on the main thread and deliver public success/error status only, with the opaque unlocked handle retained privately by startup coordination. Cancel stays responsive while cryptography runs: check its predicate before and after KDF/encryption/decryption and before publication. Those library calls cannot promise instantaneous interruption; wait for the worker to reach a safe boundary, discard its private result and destroy the root. After accepting successful unlock, use the private validated factory described above to construct the service without a second KDF. If cancellation occurs after service initialization has begun, close the newly initialized service and root through the existing ordered cleanup; it is not a rollback of successful identity publication or subsequent ordinary startup persistence.

GUI cancellation raises the safe `identity_unlock_cancelled` outcome to `main`, which prints `SPARC launch canceled.` and returns exit status `130`. Normal GUI errors retain existing exit status `1`; Tk unavailable remains `2`. A canceled GUI launch has no resource leak or hidden running worker/listener after it returns.

`python -m sparc --check` becomes strictly read-only. It prints existing version diagnostics and identity status; absent is a successful environment diagnostic with `Public fingerprint: unavailable (identity absent)`, no directory/file creation. Version 1 reports `legacy unencrypted; migration required`. Version 2 reports `encrypted; locked; private key not verified`, and prints `Public fingerprint (unverified stored metadata): ...`. It must not claim the ciphertext is decryptable or that private/public keys match. Invalid envelope/public schema returns `1` without mutation. No prompt, migration, permission tightening, Tk import, service creation or optional analysis/traffic import occurs. The current check test's implicit identity creation expectation must change; use explicitly provisioned fixtures to test persisted fingerprints.

Terminal unlock is used by the existing simulation CLI and any explicitly supplied terminal adapter, not by `--check`. Use hidden `getpass` entry and confirmation. Treat no usable terminal or `GetPassWarning` as `identity_credentials_required` rather than accepting echoing stdin fallback. Ctrl-C and EOF terminate with `identity_unlock_cancelled` and CLI status `130`, without a traceback or newly created identity. [Python getpass fallback behavior](https://docs.python.org/3/library/getpass.html)

`run_simulation(..., *, credential_provider=None)` requires an explicit provider capable of identifying each peer's public request. The command-line adapter prompts in the coordinator, sequentially for Alice and Bob, before starting networking. Credentials travel to spawn children only over a private owned multiprocessing pipe in a dedicated bounded startup exchange; never through OS argv/env/files or generic evidence projection. Children call `PeerService` with a one-use in-memory provider. Reports contain public results and fixed safe error codes only. Existing encrypted peer state requires its actual user-provided passphrase on reuse; no fixed simulation secret and no silently generated disposable credential for persistent simulation identities. Preserve simulation deadlines/cleanup around startup failures.

Existing programmatic constructors/tests migrate to explicit random in-memory credential fixtures, stable within each data directory for the test lifetime. No fixture is a production fallback, and no fixture emits its credential in assertions/reports. Pure in-memory identity objects used by handshake/audit tests require no encryption because they are not persisted. Standalone analysis and traffic entry points remain independent of identity unlock; startup KDF work must not enter record/handshake operation metrics or benchmark timing.
